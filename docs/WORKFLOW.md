# 開発の流れ

issue 駆動。人間は「何を作るか」と「いつ出すか」を決め、AIはその間を進める。

```
issue(proposed) → 人間が確認して ready → AI が実装して PR → CI → 人間がマージ → (配備・確認) → close
```

## 役割

| 工程 | 人間 | AI |
|---|---|---|
| 仕事を決める | タスク issue を書く(または、AIの下書きを直す) | issue の下書きを `proposed` で書く |
| 着手の承認 | 受け入れ条件を確認し、`ready` を付ける | `ready` が付くまで着手しない |
| 受け入れ条件 | 必要なら、`tests/acceptance` にテストとして書く(保護パス) | 条件のとおりに実装する。テストは変えない |
| 実装 | 割り込みだけ(`priority:now`) | 失敗するテスト → 最小の実装 → `fast` → レビュー → PR |
| マージ | マージする | しない |
| 使ってみる | フィードバックの issue を書く | 受け取って、タスクに分ける |

## ルール

- `ready` を付けた時点で、受け入れ条件は変更不可。変えたいときは、新しい issue にする。
- AIが起票した issue は `proposed`。人間のアカウントが付けた `ready` だけが、実装の根拠になる。
- 実装する PR が保護パス(`protected-paths.json`)を変更すると、CI が落ちる。人間が必要と判断したときだけ、`protected-change` ラベルを付ける。付けても、CODEOWNERS のレビューは必要。
- 人間への質問は、issue コメントに、質問、判断材料、既定案と期限を書き、`needs-answer` を付けて終了する。返事が来たら、新しいセッションで再開する。
- 認証・課金・データの削除・権限に関わる判断は、既定案を付けずに止める。
- 連続して失敗したら、同じことを繰り返さず、小さい子 issue に分けて、何を試して失敗したかを残す。

## 優先度

`tier:1`(いま困っていること)→ `tier:2`(できることが増える)→ `tier:3`(使い心地)→ `tier:4`(リファクタリング)の順。同じ tier では、古いものから。`priority:now` は、走っている作業を止めず、次に空いた枠に最優先で入れる。
